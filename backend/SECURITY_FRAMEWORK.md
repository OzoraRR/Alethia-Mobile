# Alethia Mobile backend security framework

**Review date:** 14 November 2026
**Scope:** the Kotlin Android client, the Next.js API service in `backend/`, and the checked-in Supabase migrations/tests.

This is a repository-based security baseline, not a penetration test or certification. The earlier browser/Netlify review is preserved as [historical material](docs/SECURITY_FRAMEWORK_WEB_LEGACY.md); it describes a different application snapshot and must not be used as evidence about this mobile backend.

## Trust boundaries

```text
Android app
  ├─ email sign-up/sign-in ───────────────> Supabase Auth
  ├─ username sign-in ──> backend API ────> private username/email RPC
  │                                      └─> Supabase Auth password exchange
  ├─ account deletion ──> backend API ────> caller-scoped account RPCs
  │                                      └─> server-key avatar cleanup
  └─ normal account data ────────────────> Supabase Data API / RPCs
                                             PostgreSQL RLS, grants, triggers
```

The Android app may contain only a Supabase publishable key and the API URL. The Supabase server secret stays in the backend environment. Standard user data operations are authorized by the caller's Supabase JWT and database policies; privileged endpoints use the server key only for narrowly scoped work.

## Controls present in the repository

## Test evidence in this checkout

The backend Node suite has 12 unit/contract tests: 4 account-deletion tests, 5 username-login tests, and 3 observability tests. The username flow tests run the handler against a local HTTP test double for the Supabase RPC and Auth endpoints. A separate `pnpm test:local-auth` test signs up a synthetic user against local Supabase Auth, resolves its email through the migrated database RPC, verifies the returned access token, rejects a wrong password, and deletes the temporary Auth user. It refuses non-local URLs and uses no hosted credentials.

On 12 November 2026, `pnpm db:reset` recreated the local database and applied all 48 migrations; 18 pgTAP files (302 assertions) and the local Auth test passed. On 14 November, the current worktree passed frozen-lockfile install, lint, typecheck, the Node suite (12 passed; the separately invoked local Auth test is skipped by default), and production build. An isolated local Supabase stack applied 49 migrations; all 19 pgTAP files (311 assertions), local Auth integration, and the local snapshot/restore rehearsal passed. After the public-profile change, the local stack applied migrations 49 and 50, and all 19 pgTAP files passed with 313 assertions. Its earlier restore summary was `49 migrations / 26 public tables / 57 public policies / 0 Auth users`. Hosted migration history now matches all 50 repository migrations. A synthetic hosted profile lookup verified the four-field response, and its test account was deleted afterward.

The latest Vercel Preview build is `READY` at `https://alethia-mobile-backend-qy3fzlgjp-ozorarr.vercel.app`; its deployed `/api/health` route returned HTTP 200 with `{"status":"ok"}`, and a synthetic unknown username returned the expected generic `401` with `Cache-Control: no-store`. Synthetic hosted signup, username login, wrong-password rejection, account deletion with an uploaded avatar, and username-login throttling passed through Preview. A read-only hosted Supabase Security Advisor scan on 14 November returned 26 findings: 19 `WARN`, 7 `INFO`, and no `ERROR`. The detailed review is in [SECURITY_ADVISOR_REVIEW.md](docs/SECURITY_ADVISOR_REVIEW.md). The warnings cover 18 authenticated-callable functions (15 caller-scoped app RPCs, two narrow identity helpers, and the public-profile projection, counted again because it is also anonymous-callable). The seven no-policy tables are deliberately closed to client roles. The owner selected a minimal public profile; migration and local plus hosted response checks are complete. Public avatar images remain a separate product setting. Do not revoke app RPC grants or add table policies only to silence the advisor. The health route does not query Supabase. The local restore rehearsal intentionally omits provider-managed objects and privileges, so it is not a hosted project restore test.
